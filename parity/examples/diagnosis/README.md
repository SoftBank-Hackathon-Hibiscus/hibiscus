# 실패 원인 분석 시연

방명록의 실제 재생 기록에서 응답 불일치 13건을 확인했습니다. AI는 이를 세션, 시작 시 DB 초기화, 컨테이너 내부 저장이라는 세 묶음으로 정리했습니다. 카드를 누르면 근거가 된 응답과 코드를 볼 수 있습니다.

발표에서는 다음 정도로 설명하면 됩니다.

> “재시작하자 로그인이 풀리고, 글이 사라집니다. AI가 실패 13건을 코드와 연결해 고칠 곳 세 군데를 짚었습니다. DB 초기화 코드를 고쳐도 교체 때 데이터가 사라지는 문제는 남습니다. 수정 범위를 확인한 뒤 같은 요청으로 다시 검사합니다.”

`실패 기록`을 눌러 목록을 잠깐 보여주고, `저장된 AI 분석`으로 돌아온 뒤 두 번째 카드를 여세요. `DROP TABLE`과 “저장소 변경도 필요하다”는 설명까지 약 30초면 보여줄 수 있습니다.

## 화면 열기

`parity/`에서 실행합니다. Python 3.10 이상과 `jsonschema`가 필요합니다. 이 명령은 Docker나 LLM을 호출하지 않습니다.

```sh
python -m pip install -r requirements.txt
python -m premortem.diagnosis \
  --bundle examples/diagnosis/guestbook --source app.py \
  --recorded examples/diagnosis/guestbook-analysis.json \
  --out premortem/.runs/diagnosis-demo
python -m http.server 5180 --bind 127.0.0.1 --directory premortem/.runs/diagnosis-demo
```

브라우저에서 `http://localhost:5180`을 엽니다. 생성된 `index.html` 하나를 다른 PC로 옮겨 직접 열어도 됩니다. 이미 있는 출력 폴더는 덮어쓰지 않으므로 다시 생성할 때는 `--out`에 새 폴더를 지정하세요.

프론트의 방명록 실패 결과에서 **저장된 LLM 진단 보기**를 누르면 새 탭으로 열립니다. `#/demos`의 **실제 실행으로 본 LLM 진단**에서도 열 수 있습니다. 화면에는 “실제 실행 · 저장된 AI 분석”과 실행 날짜를 표시하며, 현재 배포의 진단으로 소개하지 않습니다. Backend API의 실시간 분석에는 연결하지 않았습니다.

## 기존 데모에 넣기

프론트의 빌드에 보고서가 포함되므로 별도 Python 서버나 API 키는 필요 없습니다. 기존처럼 `frontend/`에서 `npm run dev` 또는 `npm run build`로 실행합니다. 보고서만 직접 열려면 `/diagnosis/guestbook.html`로 이동하세요. 새 탭을 닫으면 원래 배포 화면을 그대로 이어갈 수 있습니다.

1. 기존 방명록 차단 결과를 보여줍니다.
2. **저장된 LLM 진단 보기**를 누릅니다. “같은 방명록의 별도 실제 실행을 분석한 기록입니다”라고 소개합니다.
3. 실패 13건을 짚고, 두 번째 원인 카드를 눌러 `DROP TABLE` 코드와 교체 때 남는 저장소 문제를 보여줍니다.
4. 탭을 닫고 기존 시연을 이어갑니다. 분석을 열거나 건너뛰어도 배포 상태와 정책 판단은 바뀌지 않습니다.

분석 화면은 한국어입니다. 약 30초를 추가하면 되고, 화면을 여는 동안 추가 LLM 호출은 없습니다. 인터넷 없이도 열리며 `frontend/public/diagnosis/guestbook.html` 하나를 복사해 예비 화면으로 쓸 수 있습니다.

프론트에 포함한 HTML을 다시 만들거나 원본 기록과 대조하려면 `parity/`에서 실행합니다. 생성 전 해시·실행 식별값·LLM 응답 검사를 거칩니다. 일반 프론트 빌드에는 Python이 필요 없습니다.

```sh
python scripts/export_diagnosis_demo.py
python scripts/export_diagnosis_demo.py --check
```

## 무엇을 확인했나

| 항목 | 결과 |
|---|---|
| 원래 실행 | 2026-10-02, `rehearsal-07d13af8ec-guestbook` |
| 조건별 일치 | none 20/20, restart 14/20, replace 13/20 |
| AI 입력 | 실패 응답 13건, 런타임 관측 2건, 원래 줄 번호를 유지한 `app.py` |
| 제외한 정보 | 정답을 적어 둔 주석·docstring, README, 정책의 해결 힌트, 인증 정보 |
| 실제 모델 응답 | 2026-10-03, `claude-sonnet-5-5`, 34.886초 |
| 사용량 | 입력 7,753 / 출력 4,521 토큰. 이 표는 채택한 응답 1회의 사용량 |
| 근거 연결 | 불일치 13건 모두 연결, 없는 요청·파일·줄 인용 없음 |

카드의 근거 건수는 4·8·5건입니다. 교체 후 DB 불일치 4건이 초기화 로직과 저장소 수명 양쪽에 연결되므로 합산하면 중복됩니다. 전체 불일치 수는 13건입니다.

실제 분석 실행은 총 3회였습니다. 앞선 2회는 출력 검사에서 거부됐고 마지막 응답을 사용합니다. SDK는 요청당 최대 1회 재시도할 수 있으므로 이 숫자는 HTTP 요청 수를 뜻하지 않습니다. 화면을 다시 열거나 `--recorded`로 생성하면 추가 호출은 없습니다.

첫 구현에서는 API 스키마 변환기가 `title` 속성까지 설명용 키로 취급해 제거하는 문제가 있었습니다. 속성 이름은 보존하도록 고치고 회귀 검사를 추가했습니다. 거부된 응답은 `diagnosis_rejected.json`으로 남기며 화면에는 유효한 분석으로 표시하지 않습니다.

## 코드와 대조한 결과

- **세션:** 전역 `SESSIONS = {}`와 `/me` 조회가 로그인 소실을 설명합니다. 모델이 인용한 로그인 부분 165–166줄에는 실제 저장문인 167줄이 빠져 있습니다. 화면은 앞뒤 2줄을 함께 보여줍니다.
- **DB 초기화:** `SCHEMA`의 `DROP TABLE`, `init_db()`의 스키마 실행이 재시작 후 게시글 소실을 설명합니다. 모델이 지목한 218줄은 `main` 선언이며, 실제 호출은 다음 줄입니다. 위치 참조 검사는 이런 의미상 부정확함까지 자동 판정하지 않습니다.
- **저장소 수명:** DB와 업로드가 컨테이너 쓰기 계층에 있다는 런타임 관측과 교체 후 손실이 일치합니다. 시작 시 초기화와 저장소 수명은 함께 고쳐야 합니다.

`notes.txt`가 남은 이유에 대해 AI는 “이 입력만으로 설명되지 않는다”고 답했습니다. 성공한 요청 목록은 AI에 주지 않았기 때문입니다. 원본 기준 기록을 별도로 대조하면 교체는 요청 10 뒤에 일어나고, 요청 15가 `PUT /uploads/notes.txt`입니다. 즉 파일이 교체 후 다시 업로드됩니다. 이 한계와 원래 AI 응답을 그대로 보존했습니다.

원본 기준 기록 SHA-256: `54bf7486712b02db86b487f1ec55e1bb00bba904bfe898f1d4baa96e9d3d4d3c`.

이 사례는 원인 분석의 가능성을 보여줍니다. 다른 앱 전반의 진단 정확도나 수정 효과를 측정한 것은 아닙니다. 소스와 산출물의 해시·실행 식별값 일치를 검사하지만 서명 진위를 새로 확인하지는 않습니다. 기록에 있는 로컬 레지스트리는 과거 실행의 주소입니다.

## 다른 실행 분석

완료된 `test-build` 폴더와 분석할 Python 파일을 명시합니다. 기본 실행은 입력과 화면만 만들며, `--live`가 있을 때만 외부 LLM을 호출합니다. 앱 코드나 배포 상태를 바꾸는 기능은 없습니다.

```sh
# 현재 셸에 ANTHROPIC_API_KEY와 PREMORTEM_LLM_MODEL을 먼저 설정합니다.
python -m pip install anthropic
python -m premortem.diagnosis \
  --bundle /path/to/completed-test --source app.py \
  --live --out premortem/.runs/new-diagnosis
```

분석 전 실행 산출물·소스 해시, 커밋, 이미지, 조건별 횟수를 대조합니다. 분석 후에는 응답 스키마, 요청·관측 ID, 파일과 줄 범위, 설명된 불일치와 미확인 불일치의 누락 여부를 검사합니다. 원인 개수는 고정하지 않습니다. 분석이 실패하면 수동 답안으로 대체하지 않습니다.

새 검사는 `python -m unittest tests.premortem.test_diagnosis -v`로 실행합니다.
