## 팀 VM 연결 확인에 필요한 자료

팀에서 전체 배포 성공을 공유한 상태입니다. 아래 표는 그 실행의 증거를 함께 대조하기 위한 요청 목록입니다.
담당은 기존 역할을 기준으로 적었으며, 자료 전달 위치와 공동 실행 시각은 함께 정합니다.

| 자료 | 함께 확인할 사람 | 확인할 내용 |
|---|---|---|
| 파이프라인 실행 ID, 앱 이름, 앱 source SHA, registry digest, 실제 테스트 산출물 | 주영 · 배포 파트 | fixture가 아닌 실제 3조건 결과인지, 어떤 앱 이미지를 검사했는지 |
| 정책 입력과 `plan.json` | 류진 | 같은 실행의 테스트 결과·식별자가 유지되는지, allow/block·대상·해결 조건 |
| 필요한 승인 기록과 서명 결과 | 승표 · 배포 파트 | 승인 필요 여부, 필요 시 요청자/승인자 분리, plan_hash·digest 결속, 서명 검증 |
| 후보·전환·배포 결과와 실행 revision/컨테이너 식별 정보 | 태현 · 준하 | 승인된 대상과 이미지로 실행했는지, 후보 검사와 실제 전환 결과 |
| 후보 URL·대표 URL, 접근 방법, 검사할 기록·노이즈 파일 및 해시 | 주영 · 배포 파트 | 같은 요청을 보낼 대상과 시점, 인증 필요 여부, 초기 데이터 상태 |

API 키·인증 토큰·서명 개인키를 PR에 붙이지 않습니다. 접근이 필요하면 팀이 사용하는 별도 전달 방식으로 설정합니다.
앱 등록 UUID, 파이프라인 실행 ID, Parity 재검사 ID는 서로 다른 값일 수 있으므로 대응 관계를 남깁니다.
공통 registry digest와 각 환경 이미지의 관계를 확인합니다. 다중 아키텍처 이미지라면 최상위 digest와
플랫폼별 이미지의 대응을 빌드 담당자와 확인하며, 로컬 이미지 ID를 registry digest로 대신 적지 않습니다.

### 같은 실행에서 대조할 순서

1. 실행 ID·앱 SHA·registry digest를 정하고 해당 실행의 실제 `result`·진단·handoff를 확보합니다.
2. `none/restart/replace`가 끝까지 실행됐는지, 완료된 불일치와 실행 중단이 구분되는지 확인합니다.
3. 정책 입력으로 변환된 결과와 `plan.json`의 판단·배포 대상이 원본 결과에 대응하는지 확인합니다.
4. 해당 계획에서 필요한 승인 및 서명 결과가 같은 plan_hash·digest에 연결되는지 확인합니다.
5. 배포 결과의 후보·검사·전환 상태와 목적지 이미지 식별 근거를 대조합니다.
6. 후보 및 대표 주소를 `verify`로 조회하고 이번 결과 파일을 같은 실행 기록에 연결합니다.

성공 흐름 외에 `block`이면 서명·배포로 진행하지 않았는지 확인합니다. 전환 전 후보 실패로 기존 버전을
유지하는 `held`는, 서비스 중 장애가 발생해 다른 환경으로 넘어가는 failover와 별도로 기록합니다.
승인이나 기타 단계가 생략됐다면 적용한 정책과 사유를 적고, 전체 승인 흐름을 확인한 것으로 표시하지 않습니다.

### 후보 주소에서 verify 실행

레포의 `parity/`에서 실행합니다. 아래 값은 전달받은 실제 파일과 주소로 바꿉니다.
실행 전에 기록·노이즈 파일의 존재와 해시, GET만 있는 기록인지 확인합니다.

```text
python -m parity verify --record "<고정된 GET 기록.jsonl>" --noise "<고정된 noise.json>" --target "<이번 후보 URL>" --out "records/<실행ID>/verify-candidate.json"
```

- 실제 명령의 종료 코드와 stdout/stderr, 결과 JSON, 대상 URL, 실행 시각을 보존합니다. 대표 주소도 별도 결과 파일에 저장합니다.
- `verify`는 Docker를 조작하거나 데이터를 초기화하지 않습니다. 이 명령에 `--conditions`나 `--container`를 넣지 않습니다.
- GET만 있는 기록에는 `--allow-writes`를 붙이지 않습니다. 상태를 만드는 요청은 담당자와 정한 검사용 환경에서 별도로 수행합니다.
- 노이즈 파일이 없으면 현재 CLI는 경고 후 모든 필드를 비교하므로, 실행 전에 파일을 대조합니다.
- 종료 코드 0은 일치, 1은 불일치, 2는 입력 등 실행 오류입니다. 연결·인증서 문제도 불일치로 나타날 수 있으므로 원인을 따로 확인합니다.
- `verify`의 `image`·`commit`은 `unknown`, `facts`는 `[]`입니다. 이미지 확인·사실 부재의 증거로 해석하지 않습니다.
- 배포 식별 정보는 별도 실행 기록에 연결합니다. 기존 결과 JSON이나 공통 계약을 임의로 확장하지 않습니다.

## 장애 전환 후 글·파일 유지 확인

### 시작 조건

- 글 작성·조회와 파일 업로드·다운로드가 가능한 검사용 앱과 대표 주소가 필요합니다.
- 배포 담당자가 정책상 `failover_allowed` 여부와 실제 데이터 저장 위치·공유 방식을 확인합니다.
- 담당자와 장애 주입·복구 시각, 작업 주체, 영향을 받는 검사용 범위를 정합니다.
- 데이터 공유 방식이 없거나 우회가 금지되어 있으면 이 검사는 대기로 둡니다. 정책을 우회하거나 복구했다고 가정하지 않습니다.

현재 health 전용 바인딩 앱으로는 이 항목을 검사할 수 없습니다. 결함을 넣은 방명록이 정책에서 차단된다면
그 앱을 억지로 배포하지 않고, 조건을 충족하는 검사용 앱을 배포 파트와 정합니다.

### 실행 순서

1. 대표 주소가 실제 온프레로 요청을 보내는지 배포 파트의 라우팅·요청 처리 기록으로 확인합니다.
2. 합의된 테스트 계정으로 고유한 글과 파일을 하나씩 저장합니다. 글 ID·본문, 파일 ID·크기·내용 SHA-256을 남깁니다.
3. 온프레에서 저장한 글과 파일을 조회해 기준을 확정합니다. 이후 비교용 기록은 조회 요청으로만 만듭니다.
4. 담당자가 합의한 장애를 발생시키고 시각·조작 내용을 기록합니다. 터널 장애인지 앱 장애인지도 구분합니다.
5. 대표 주소가 클라우드로 전환됐다는 라우팅·요청 처리 근거를 확보합니다. HTTP 200이나 동일 URL만으로 전환을 판단하지 않습니다.
6. 같은 대표 주소에서 같은 글 ID·본문을 조회하고, 같은 파일을 다운로드해 내용 해시를 비교합니다.
7. 담당자가 복구한 뒤 라우팅 상태와 테스트 데이터 정리 여부를 기록합니다.

전환 뒤 글·파일을 다시 생성하거나 수동 복사해 결과를 맞추지 않습니다. 파일 목록에 이름이 보이는 것만으로
내용이 유지됐다고 판단하지 않으며, Parity 응답 비교와 별도로 다운로드한 파일 바이트의 SHA-256을 대조합니다.
동시 쓰기·전환 중 요청 재시도·중복 저장·장기적인 무손실까지는 이 작은 시험의 보장 범위에 포함하지 않습니다.
