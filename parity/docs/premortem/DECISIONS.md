# 결정 기록

결정마다 다른 방법을 뭘 봤는지, 왜 안 골랐는지 적습니다. "팀 합의"라고 쓴 것만 회의에서 정해진 것이고, "제안"은 아직 팀원 확인 전입니다.

## 모듈 안에서 정한 것

| # | 날짜 | 고른 방법 | 검토한 다른 방법 | 안 고른 이유 |
| --- | --- | --- | --- | --- |
| 1 | 9/30 | restart와 replace를 따로 시험 | restart만 시험 | restart는 같은 컨테이너를 다시 켜서 컨테이너 안 파일이 남는다. 실측에서도 restart 6/6, replace 4/6으로 결과가 갈렸다 |
| 2 | 9/30 | 요청 번호를 기준으로 조건을 직접 넣음 | Pumba, Toxiproxy 같은 장애 주입 도구 | 도구가 나빠서가 아니라, 같은 기록·같은 이미지·같은 초기 상태에서 "3번 응답 뒤"를 정확히 맞춰야 none과 비교가 되기 때문. 이 조건 하나를 위해 도구를 더 들이면 설명할 것만 늘어난다 |
| 3 | 9/30 | AI 수정은 before/after 문자열 치환만 받음 | AI가 diff를 직접 쓰거나 명령 실행 | 적용하기 전에 경로, 일치 횟수, 수정량을 프로그램이 확인할 수 있다. diff를 직접 받으면 줄 번호가 어긋나거나 파일을 새로 만드는 걸 막기 어렵다 |
| 4 | 9/30 | 복사본에만 적용하고 사람 검토 대기 | 원본 수정, 자동 PR | AI가 틀려도 원본은 안전하다. PR 발행은 권한이 필요한 일이라 P1으로 미룸 |
| 5 | 9/30 | 다시 검사할 때 원래 기록·노이즈 그대로 | 수정 후 노이즈 다시 학습 | 기준을 새로 만들면 새로 생긴 오류가 노이즈로 숨는다. 기준이 바뀌면 재검증을 거부한다(BASELINE_CHANGED) |
| 6 | 9/30 | AI에는 도구 없이 JSON만 요청 | AI에 셸·Docker 도구 제공 | 로그나 코드에 이상한 지시문이 있어도 AI가 할 수 있는 일이 없다. 팀 보안 원칙(AI는 권한 없음)과 같은 방향 |
| 7 | 9/30 | Python, 파트 사이는 JSON 파일 | 정책 파트와 같은 TypeScript | 윤선님 재생기가 Python이라 바로 붙인다. 류진님과는 JSON 파일로 주고받는 팀 방식(류진님 D3)을 따른다 |
| 8 | 9/30 | 바깥 준비 확인이 실패하면 컨테이너 안 health와 LISTEN 주소까지 보고 "binding 후보"로만 표시 | 시간 초과가 나면 바인딩 문제로 판단 | 시간 초과만으로는 앱이 느린 건지, 포트가 틀린 건지, 바인딩 문제인지 모른다. 포트가 다르면 "원인 미확정"으로 남긴다 |
| 9 | 9/30 | 증거 ID를 실행마다 같게 (예: replace-http_mismatch-4) | 무작위 ID | 녹화해 둔 AI 응답을 새 실행에서 다시 검사할 수 있다. 무작위면 녹화 응답이 매번 "없는 증거"로 거부된다 |
| 10 | 9/30 | 시연은 녹화된 실제 응답으로, 이번 실행에서 호출 안 했다고 표시 | 발표 중 매번 실제 호출 | 발표 중 네트워크나 응답 차이로 흔들리지 않는다. 녹화도 같은 검사를 거친다. 류진님 D16과 같은 방식 |
| 11 | 9/30 | 테스트 컨테이너는 루프백에만 포트 게시, 권한 최소화, 환경변수·볼륨 안 넘김 | docker run 기본값 | 다른 컨테이너나 호스트에 영향이 없어야 한다. 다만 바깥 네트워크 차단은 안 했다. 포트 게시에 bridge 네트워크가 필요해서다(샘플 앱은 신뢰하는 코드) |
| 12 | 9/30 | 재생기에서 오류가 나면 그 조건을 "도구 오류"로 기록 | 오류를 그대로 올려 실행 중단 | 결과 파일이 남아야 무슨 일이 있었는지 볼 수 있다. 몇 건 보냈는지 모르면 실행 수 0, 통과로 안 셈 (개발일지 #1) |

## 팀 합의 (9/30 전체 회의)

| # | 정해진 것 | 이 모듈에 미치는 영향 |
| --- | --- | --- |
| T1 | 파이프라인은 GitHub App PR webhook → 서비스가 실행. 수동 실행도 둠 | AI 수정안을 PR로 올리면 파이프라인이 처음부터 다시 도는 흐름과 잘 맞음. MVP 범위는 목요일 오후에 정함 |
| T2 | 이미지는 테스트/검증 단계에서 빌드, 테스트부터 배포까지 같은 digest | 테스트 파트가 빌드와 digest 전달을 맡음. 누가 할지는 윤선님과 스레드에서 정함 |
| T3 | 공통 식별값은 레지스트리 digest. 레지스트리 위치는 미결 | 지금 결과의 registry_digest가 null인 부분을 채울 수 있게 됨. 위치가 정해지면 연결 |
| T4 | contracts/는 팀 공용, JSON Schema가 원본, 변경은 PR과 Slack | env_report를 변환기가 읽게 되면 스키마를 contracts/에 PR로 올림 |
| T5 | local은 개발자 PC, onprem은 자체 서버, cloud_run은 Cloud Run | 명세의 "local은 온프레 뜻이라 바꾸지 않는다" 규칙은 이 합의로 바뀜. 이 모듈은 정책 target 이름을 그대로 넘기기만 함 |
| T6 | 목요일 점심 전후 코드 올리기와 스레드 결론, 목요일 오후 첫 연결 범위·MVP, 금요일 오후 리허설 | 윤선님 재생기 연결은 목요일 오전 목표 |
| T7 | LLM API 키와 비용은 승표님 담당 | 실제 AI 호출은 승표님께 키를 받아서 |
